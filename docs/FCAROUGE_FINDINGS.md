# Findings for the FrancoisCarouge projects

Blocking findings, and findings that prevent performance improvements or let regressions through, in
[FrancoisCarouge/Kalman](https://github.com/FrancoisCarouge/Kalman) and
[FrancoisCarouge/TypedLinearAlgebra](https://github.com/FrancoisCarouge/TypedLinearAlgebra), found while
integrating them into ArduPilot. See [FCAROUGE_KALMAN_PLAN.md](FCAROUGE_KALMAN_PLAN.md) for the
integration plan. Resolved findings are removed, and positive, usability, packaging and process notes
are not kept (owner, 2026-10-18); numbers are not reused.

Rechecked on 2026-10-20 against Kalman a241cc447, TypedLinearAlgebra 7fed28c59 and mp-units ef8653eab (pinned back, F13).

| F7 | Kalman | Features (EKF3) | ArduPilot's 24-state EKF needs: sequential scalar fusion (one row of H per update), state masking (inhibited states), access to the innovation and its covariance S, update rejection (innovation gating), a replaceable covariance prediction (generated sparse code), and post-update hooks (symmetrisation, variance clamping, state limits). | `AP_NavEKF3`, `EKFGSF_yaw`, `Airspeed_Calibration`, `AP_Soaring`.; 2026-10-11, `EKFGSF_yaw` port: the innovation gate and 5-sigma compression need the innovation and S before the state is corrected, so ArduPilot computes the innovation and its variance itself, then lets `update()` compute them again; a rejected update is simply not called; the compression is passed through a modified measurement; variance limits and symmetry are applied by reading and writing `p()` after each step | Customization points for each; see Phase 2. A two-stage update (innovation, then correction, with the innovation readable and scalable in between) would cover gating, compression and rejection. | open |
| F8 | Kalman | Features | The update equation is fixed to the Joseph form by default; ArduPilot filters use the simple form `P -= K * P12'` followed by symmetrisation. Equivalence with the existing filters needs a selectable update form. | `AP_Soaring/ExtendedKalmanFilter.cpp`, `Airspeed_Calibration.cpp`. | Make the covariance update form a customization point (Joseph, simple, simple plus symmetrise). | open |

| F14 | TLA | Docs, embedded | Using the mp-units support in an embedded, `-fno-exceptions`, `-Werror=undef` build needs undocumented setup: mp-units must be included as system headers (its headers test undefined macros such as `MP_UNITS_COMP_MSVC`), and `MP_UNITS_HOSTED=0` is required because the hosted `inplace_vector::emplace_back` throws. | F17 | Both | Packaging | The mp-units `element_caster` specializations are defined twice, in Kalman's `support/mp_units/fcarouge/mp_units.hpp` and in TypedLinearAlgebra's file of the same path and name: including both redefines them, and putting both directories on an include path makes one shadow the other. | Both files.; 2026-10-18: after Kalman d80652ace the two files share their path and name; ArduPilot includes Kalman's integration headers by a path below `support/` to avoid the shadowing | Keep one owner (TypedLinearAlgebra) and have Kalman use it. | open |
| F22 | Both | Build | Compile cost per translation unit (g++ 15, `-O2`): `kalman.hpp` 2.2 s / 154 MB, `typed_linear_algebra.hpp` 2.1 s / 185 MB (about 1.3 s of each is `<format>`/`<print>`, included even when nothing is formatted), with TypedLinearAlgebra's mp-units support 5.8 s / 383 MB. | F23 | Kalman | Usability | Supported filter configurations are an enumerated list: a configuration without initial P, Q and R (set later, as ArduPilot does on each thermal entry) fails with "This requested filter configuration is not yet supported" without saying which configurations are accepted. | `kalman_internal/factory.hpp:69`.; 2026-10-09: the airspeed calibration (callable H and observation, no prediction arguments) fails with the same message until an empty `prediction_types<>` is passed; 2026-10-11: the EKFGSF yaw filter has a nonlinear transition whose Jacobian F and process noise Q depend on the prediction arguments and the state: no configuration combines a `transition` function with callable F and Q (callable F exists only for the linear `x = F x + G u`), so ArduPilot sets `f()` and `q()` before each `predict()`, although the README documents `f` and `q` as configurable callables | Default P, Q and R to zero when omitted, and list the accepted configurations in the diagnostic. | open |
| F25 | TLA | Build | `typed_matrix::data()` returns `std::forward_like<decltype(self)>(self.storage)`. With clang (20, 21) and Ubuntu 24.04's default libstdc++ 14.2, whose `std::forward_like` has a deduced `decltype(auto)` return type, this fails: "function 'forward_like<...>' with deduced return type cannot be used before it is defined". libstdc++ 14.3 and 15 rewrote it with an explicit return type and work. | CI `test unit tests and sitl building (clang, ...)` on `test_linear_algebra`; libstdc++ `bits/move.h` 14.2 versus 14.3. | Avoid `std::forward_like` (an explicit cast on the deduced `self` category), or document libstdc++ >= 14.3 for clang. | open |
| F26 | TLA | Features | No typed block, segment or concatenation operations: a heterogeneous state vector such as EKF3's 24 states is used by groups (velocity, position, biases), and covariance updates work on blocks, but TypedLinearAlgebra only offers element access (`at<i>()`) and whole-matrix algorithms. Mapping EKF3's union of a state struct and a `Vector24` onto one typed vector would need per-element code. Nested typed matrices (`support/nested_typed_eigen`) may be the intended route; undocumented for this use. | TypedLinearAlgebra public API and README; EKF3 `state_elements`.; 2026-10-11: the EKFGSF innovation variance is the velocity block of the covariance plus R, the dense `H * P * transposed(H) + R` with a selector H, for want of a block, cost stack (F38), so ArduPilot reads the four elements as quantities; 2026-10-13: an EKF3 observation Jacobian has 2 to 6 non-zero elements of 24 (5 for the true airspeed), which the generated code exploits and a dense typed row cannot: `P * transposed(H)` and `H * P` do 24 terms per element instead of 5 | Typed `block<Row, Column, Rows, Columns>()` views or copies with their element types, and concatenation of typed vectors, or documented guidance for grouped states. A typed selection of rows or columns by a compile-time index list would serve both the grouped states and the sparse Jacobians. | open |
| F28 | TLA | Embedded | No compound assignment (`+=`, `-=`, `*=`) and no in-place algorithms: every typed operation returns a new matrix, and the wrappers copy whole backend matrices. `JTJ = JTJ + transposed(J) * J` on 9x9 floats needs a 1336 B stack frame on Cortex-M7 (ArduPilot limit 1300 B, `-Werror=frame-larger-than`), where the hand-written loop needs none beyond JTJ. ArduPilot works around it by type-checking the expression with an unevaluated `decltype` and accumulating on the backend storage. | `AP_AccelCal/AccelCalibrator.cpp` (CubeOrange, MatekF405 builds); again in `AP_Compass/CompassCalibrator.cpp`, where JTJ is also damped in place twice instead of copied, to fit the 2048 B calibration thread stack.; 2026-10-11: TypedLinearAlgebra 1b91a3678 adds an in-place `matrix_rank_1_update(x, y, a, a)`, exactly the accumulation needed, next to `add`, `matrix_product` and `scale`, but these exist only under `__cpp_lib_linalg` and delegate to `std::linalg` over `mdspan`: unavailable with libstdc++ 14 and 15, Arm GCC 15.2, and an owning backend such as ArduPilot's, so the workaround stays; 2026-10-13: for one scalar fusion on a 24-state typed covariance (EKF3), `P = P - K * transposed(PHt)` takes a stack frame of 9528 bytes in single precision and 19048 in double on Cortex-M7, against 608 and 1200 with the update done in place on the storage | Compound assignment operators delegating to the backend's in-place operations, and move/forwarding through `make_typed_matrix` so temporaries are not copied. Offer the in-place algorithms without `<linalg>`, through a backend dispatch as `transposed` has. | open, partly addressed |
| F29 | TLA | Embedded, build | `typed_linear_algebra.hpp` always includes the `std::chrono` integration (`chrono.tpp`, `<chrono>`) and `<format>`. ArduPilot saves and restores the macros around the includes. | MatekF405 copter build with the typed accelerometer calibrator; `AP_HAL/AP_HAL_Macros.h`. | Make the chrono and format integrations opt-in headers; keep the core header to `<tuple>`, `<concepts>`, `<utility>`. | open |
| F35 | Kalman | Embedded | A filter object stores every intermediate of its last step as a member: gain, innovation and its covariance, output, output and transition models, and the last update and prediction arguments, besides the state and covariances. The 3-state airspeed calibration filter is 180 bytes where the hand-written one kept 56 (state, covariance, two noise constants), the 2-state precision landing filter 116 bytes where it kept 20; ArduPilot holds two airspeed calibrations and two landing filters per vehicle. | `sizeof` of the `AP_Airspeed` and `AC_PrecLand` filters (SITL, Cortex-M4/M7 identical).; 2026-10-11: each 3-state, 2-output EKFGSF filter holds 58 scalars where the state, covariance, innovation and its variance took 18; the estimator, five filters, grows from 1712 to 3592 bytes with a double precision EKF and from 856 to 1824 bytes in single precision, allocated once per EKF core | Keep only the state and covariances (and what the getters must return) as members, computing the rest as locals of `update()`/`predict()`, or make the stored intermediates opt-in. | open |
| F37 | Kalman | Embedded, performance | The update and prediction are dense, general matrix expressions: `S = H P H' + R`, the gain by a general division, the Joseph form `(I - K H) P (I - K H)' + K R K'`, `F P F' + Q`, each operation returning a new matrix (F28). Against the generated sparse scalar code they replace in the EKFGSF yaw estimator (H selects two states, F differs from the identity by two elements), the bank of five corrections takes 1203 ns instead of 271 ns, and the five predictions with their unchanged attitude filters 1019 ns instead of 550 ns (x86-64, g++ 15, double precision; 1049 against 212 ns and 913 against 481 ns in single precision). Flash: 7392 bytes more on CubeOrange, 6704 on MatekF405. The prediction runs at the EKF rate for each EKF core. | Timing of `EKFGSF_yaw::update()` and `fuseVelData()` over 200 simulated 30 s flights, previous and typed implementations side by side. | A selectable simple covariance update (F8), scalar sequential updates (F7), in-place operations (F28), and no stored intermediates (F35); a benchmark against hand-written code for a small filter in the library's own suite would track it. | open |
| F38 | Kalman | Embedded | Stack: `update()` evaluates each equation as one expression whose temporaries all live at once, and the Joseph form computes `i - k * h` twice. For a 3-state, 2-output filter in double precision its stack frame is 1416 bytes on Cortex-M7 (1504 with saved registers), above ArduPilot's 1300 byte limit per function (`-Werror=frame-larger-than`), which no code outside the library can reduce; `predict()` with its caller takes 872 bytes, constructing the filter 632. The generated scalar code it replaces used 288 bytes for a correction and 96 for a prediction; the flight controller's main thread has 7168 bytes. | `-fstack-usage` of `AP_NavEKF/EKFGSF_yaw.cpp` for CubeOrange (Arm GCC 15.2): the error is reported in `x_z_p_q_r_hh_f_us_ps.hpp`. ArduPilot calls the update from a function of its own and raises the limit to 1500 bytes for that file, as its double precision EKF cores already do.; scaling probe (N states, one output, Cortex-M7, Arm GCC 15.2 `-O2`), frames of `update()` / `predict()` in bytes: N=3 float 680 / 304, double 1816 / 552; N=9 float 4152 / 2296, double 8200 / 4560; N=24 float 28192 / 16152, double 56328 / 32280, that is about 12.5 and 7 state-sized matrices. Constructing a filter as a global takes a static initialization frame of 2080 (N=9 float) to 28248 bytes (N=24 double). Experiment on a copy of the header: evaluating in steps with named intermediates gives 2448 / 1968 (N=9 float) and 32896 / 27672 (N=24 double); with the simple covariance update in place of the Joseph form 1432 and 18864 for `update()` | Evaluate the update in steps that reuse the filter's members (they exist: `k`, `s`, `y`) and one scratch matrix, with in-place operations (F28) and the simple covariance form as an option (F8); report stack use per sample in the embedded CI job of F4. Steps alone recover 40%, not enough at 9 states and far from it at 24: both libraries need operations that write into an existing matrix. This blocks the gimbal EKF and EKF3 on a flight controller. | open |
| F39 | TLA | Embedded | Constructing a large heterogeneous typed vector from its elements, `typed_row_vector<M, E0, ..., E23>{e0, ..., e23}`, emits a non-inlined `for_constexpr_detail<0, ..., 23>` function of about 1.2 kB on Cortex-M4 for each vector type (element casters applied one by one), and is slow: selecting the row and column of a 24-state covariance this way for six observation indexes added 21.9 kB of flash to a MatekF405 copter and made the fusion 7 times slower than the scalar code on the host. Copying the backend storage when the element types are the same costs nothing. | `AP_LinearAlgebra::row()`/`column()` first version, EKF3 `FuseVelPosNED`, `arm-none-eabi-nm -S` of the firmware (77 typed symbols, 44 kB). | When source and destination element types are identical, or the element casters are the identity, construct and convert by copying the storage; otherwise keep the per-element path. A block or selection API (F26) would avoid the construction altogether. | open |
| F40 | Kalman | Missing functionality | Several ArduPilot filters cannot be written as a Kalman library filter, only beside it with TypedLinearAlgebra: the EKF3 and EKF2 24-state filters (scalar fusions of observations of different types on one state: m/s, unitless, m/s/s, gauss, rad, m, rad/s; gains masked per inhibited state and a state count that changes, `stateIndexLim`; innovation gating between the innovation and the correction, and a variance-only mode for gating diagnostics; covariance clamping and symmetrization after each fusion; a generated covariance prediction), the Solo gimbal EKF (9 error states, the quaternion kept outside and reset from the angle error after each fusion, scalar fusions of velocity in m/s and heading in rad), the EKF3 beacon alignment filter (3 states in m, range observations gated except before alignment, `K H P` clamped to the variances, symmetrization, the vertical state replaced between updates) and its two 1-state vertical offset filters (gated except while aligning, innovation variance floored), and the EKF3 terrain offset estimator (one state in m, a range observation in m and two flow observations in rad/s, each gated before its correction, the state clamped below the vehicle and the variance floored after it). A filter has one output type, one update form, no step between innovation and correction, and no hook after it. The filters the library does host needed workarounds recorded elsewhere: fixed storage constructed at run time (F21), stored intermediates (F35), stack (F38), time (F37). | EKF3 fusions ported with TypedLinearAlgebra alone (plan, Phase 7 log, 2026-10-13 to 2026-10-15); gimbal EKF assessment (2026-10-11); `EstimateTerrainOffset`, read 2026-10-15, which the plan first meant to put on the library as the AGL filter. Thermal EKF, precision landing, airspeed calibration, EKFGSF bank and AGL filters are on the library. | Add these filters as samples of the Kalman library, each one a target for the features it lacks (F7, F8) and a regression test once they exist: the terrain offset estimator (smallest: several output types and gating on one state), the gimbal EKF (error state with reset, 9 states, stack), an EKF3 subset (scalar fusions with masks). The hosted ones make samples too, as embedded examples with units. 2026-10-15: the terrain offset estimator written as Kalman sample `ekf_1x1x0_terrain_estimation` (branch `sample-terrain`), from the published model: it builds and runs untyped, with R set before each update, the consistency test recomputed outside the filter, and the constraint applied after the update, each a `@todo`; a typed version cannot be declared (outputs in m and rad/s). Then the beacon alignment filter (`ekf_3x1x0_beacon_position`, branch `sample-beacon`: gate outside the filter after alignment, the limited covariance correction a `@todo`) and the gimbal EKF (`ekf_9x1x0_gimbal_attitude`, branch `sample-gimbal`: error-state reset through `x()`, F set with `f()` before each prediction because no configuration combines a callable F with prediction arguments and a callable H with update arguments, `hh_ff_us_ps`). ArduPilot is GPL 3 and the Kalman library is under the Unlicense: the samples must be written from the published models, not copied from ArduPilot's source. | open |
| F43 | TLA | Correctness | The unit is dropped when a typed vector is built from a tuple-like value: `velocities state{q};`, where `q` is in m/s and the elements are declared in km/h, stores the m/s numbers unchanged, 10 m/s becoming 10 km/h instead of 36 km/h, without a diagnostic. Two places cause it: the constructor `typed_matrix(const other_tuple_like_vector<typed_matrix> auto&)` passes the source element straight to `cast<underlying, element<i>>(get<i>(value))` without converting it to `element<i>` first, and the mp-units `element_caster` (`support/mp_units/fcarouge/mp_units.hpp`) returns `quantity_cast<spec>(value).numerical_value_in(specified.unit)`, the number in the source's unit rather than in the element's declared unit. | Reported by the owner, 2026-10-20. ArduPilot's typed vectors declare every element in its SI unit, so a source in another unit does not occur there. | Convert first, `cast<underlying, element<i>>(element<i>{get<i>(value)})`, which also brings mp-units' unit, truncation and kind checks; in the caster, read the number in `From`'s unit (`get_unit(reference)`). Worth checking: the forcing `quantity_cast<spec>` may also let a wrong axis into a slot, for example a lateral velocity into a forward velocity element. Tracked with its fix and tests in TypedLinearAlgebra's `todo` `TODO.md`. | open |
