# Findings for the FrancoisCarouge projects

Shortcomings, frictions and improvement opportunities in
[FrancoisCarouge/Kalman](https://github.com/FrancoisCarouge/Kalman) and
[FrancoisCarouge/TypedLinearAlgebra](https://github.com/FrancoisCarouge/TypedLinearAlgebra), found while
integrating them into ArduPilot. See [FCAROUGE_KALMAN_PLAN.md](FCAROUGE_KALMAN_PLAN.md) for the
integration plan.

Status: open (not reported upstream yet), reported, fixed (with the upstream version).

All findings were rechecked on 2026-10-09 against Kalman ae8146d7b, TypedLinearAlgebra c9a5c2b and mp-units 132b590d2; those not annotated otherwise are unchanged.
Library versions examined: Kalman `2fbb1e2`, TypedLinearAlgebra `8eb0b1c` (2026-10-05).

| ID | Library | Kind | Finding | Evidence | Suggestion | Status |
|---|---|---|---|---|---|---|
| F1 | Kalman | Embedded | `kalman_internal::function` type-erases callables with `std::make_unique` and virtual dispatch; constructing or reassigning a callable allocates. ArduPilot forbids heap allocation after init. | `kalman_internal/function.hpp:53,56` (the file's own `@todo` asks for small-storage alternatives). | Store callables by value in the filter type (template parameter, no type erasure), or a fixed-capacity inline buffer with a static size check. | fixed (Kalman 2301ab7cd: callables stored as their own types; the thermal EKF object no longer references `operator new`/`delete`, its SITL code shrinks from 70.9 kB to 4.5 kB, `Plane.Soaring` passes) |
| F2 | Kalman | Embedded, build | `kalman.hpp` always includes `<print>` and `<format>` through `print.hpp` and `format.hpp`, even when no formatting is used, and declares `inline constexpr printer print` so the headers cannot be skipped. Blocker for ArduPilot firmware: ArduPilot's ChibiOS build replaces `stdio.h` with a minimal header without `FILE` or `fwrite`, so `<print>` fails (`'fwrite' is not a member of 'std'`) and no Kalman filter can build for a flight controller. Also fails on GCC 13's libstdc++ and costs about 1.3 s of compile time per translation unit (F22). | `kalman.hpp:51-52,505`, `kalman_internal/print.hpp:44`; CubeOrange plane build with the Kalman soaring EKF; `libraries/AP_HAL_ChibiOS/hwdef/common/stdio.h`. | Move printing and formatting to opt-in headers (for example `fcarouge/kalman_print.hpp`), so `kalman.hpp` needs neither `<print>` nor `<format>`. | open, no longer blocking: ArduPilot's ChibiOS `cstdio` declares the names `<print>` uses, bound to undefined symbols (a call fails to link); the compile time cost remains |
| F3 | Both | Docs | Minimum compilers are documented differently: Kalman says "Clang 20+, GCC 14+", TLA says "Clang with libc++, GCC 14+". Measured: both libraries alone build with clang 19-21 and libstdc++ 15, but with TypedLinearAlgebra's mp-units support clang 19 fails on libstdc++ 15 `<format>` (`conflicting types for 'make_format_args'`), while clang 19 with libc++ and clang 20+ with libstdc++ 15 work. clang 18 fails on libstdc++ 15 `<format>` even without mp-units. | Probes on g++-14/15, clang++-18/19/20/21 (libstdc++ 15, libc++), Arm GCC 15.2. | Document one tested matrix (compiler x standard library x optional integration) for both projects, and test the floor in CI. | fixed (Kalman ae8146d7b, TypedLinearAlgebra c9a5c2b: both document the same CI-tested compilers, clang 20 and 21, GCC 14 and 15) |
| F4 | Both | Embedded, CI | No CI coverage of a freestanding-like embedded configuration. Both libraries happen to build cleanly for Cortex-M4/M7 with `-fno-exceptions -fno-rtti -fsingle-precision-constant -Wdouble-promotion -Werror=shadow,undef,float-equal`, but nothing guards it. | Phase 0 probes with Arm GCC 15.2.; 2026-10-09: both projects added a real-time sanitizer CI job (host), still no `arm-none-eabi` cross build | Add a CI job cross-compiling the samples for `arm-none-eabi` with those flags and a code size report. | open |
| F5 | TLA | Usability | The requirements on a backend matrix type are not documented. They are discovered from errors deep in the implementation, e.g. a missing `operator()(std::size_t)` reports `no match for call to (fixed_matrix) (std::size_t)` in `typed_linear_algebra.tpp`. | Phase 0 probe backend. | Document the backend contract (element access forms, arithmetic, `transpose`, `Zero`) and check it with a named concept and a readable `static_assert` at `typed_matrix` instantiation. | open |
| F6 | TLA, Kalman | Embedded | No owning, fixed-size, allocation-free backend ships with the libraries. The `std` backends wrap non-owning `std::mdspan` views over Kokkos' reference `std::linalg`; Eigen and Armadillo are heavy for microcontrollers. | `support/chrono_std`, `support/kokkos`. A 30-line owning `float[R*C]` backend was enough for the probe (102 bytes of code on Cortex-M4). | Ship a minimal owning fixed-size backend in `support/` as the embedded reference. | open |
| F7 | Kalman | Features (EKF3) | ArduPilot's 24-state EKF needs: sequential scalar fusion (one row of H per update), state masking (inhibited states), access to the innovation and its covariance S, update rejection (innovation gating), a replaceable covariance prediction (generated sparse code), and post-update hooks (symmetrisation, variance clamping, state limits). | `AP_NavEKF3`, `EKFGSF_yaw`, `Airspeed_Calibration`, `AP_Soaring`. | Customization points for each; see Phase 2. | open |
| F8 | Kalman | Features | The update equation is fixed to the Joseph form by default; ArduPilot filters use the simple form `P -= K * P12'` followed by symmetrisation. Equivalence with the existing filters needs a selectable update form. | `AP_Soaring/ExtendedKalmanFilter.cpp`, `Airspeed_Calibration.cpp`. | Make the covariance update form a customization point (Joseph, simple, simple plus symmetrise). | open |
| F9 | Both | Process | Both projects change daily (several commits on 2026-10-04 and 2026-10-05). A consumer that pins versions needs frequent tagged releases and a changelog entry per release. | `git log` of both repositories. TLA has `CHANGELOG.md`; Kalman gained one on 2026-10-05. | Tag releases (semantic versioning) whenever the public API or requirements change. | open |
| F10 | TLA | Positive | Unit mismatches give a clear compile-time message ("Matrix addition requires compatible element types") and the typing has no code-size cost. | Phase 0 probe. | Keep; worth showcasing in the README. | n/a |
| F11 | Both | Process | Release tags lag behind the declared versions: the headers say Kalman 0.5.4 and TypedLinearAlgebra 0.4.0, but the latest tags are Kalman `0.5.3` (2026-03-16, seven months of changes since) and TypedLinearAlgebra `0.3.0` (2026-09-12). A consumer pinning a tag gets old code; pinning `master` gets moving code. | `git ls-remote --tags`; the `Version` line of `kalman.hpp` and `typed_linear_algebra.hpp` and the `project(VERSION)` of both `CMakeLists.txt`. Both tags pass the Phase 0 probes. | Tag each version when the header version is bumped (or bump the header only when tagging). | open |
| F12 | Kalman | Build | Kalman fetches TypedLinearAlgebra with `FetchContent_Declare` and no `GIT_TAG`, so every Kalman build uses TypedLinearAlgebra `master` at that moment: builds are not reproducible and no Kalman version names a compatible TypedLinearAlgebra version. | `support/typed/CMakeLists.txt` (both at tag `0.5.3` and at `master`). | Pin `GIT_TAG` to a TypedLinearAlgebra release and document the compatible version pair. | open |
| F13 | TLA | Build | TypedLinearAlgebra's mp-units support needs unreleased mp-units: `support/mp_units/fcarouge/mp_units.hpp` includes `mp-units/framework/vector_components.h`, which exists on mp-units `master` (2026-10-01) but not in the latest release v2.5.0, and `support/mp_units/CMakeLists.txt` fetches mp-units without `GIT_TAG`. | mp-units v2.5.0 and `master` trees. | Pin the mp-units commit (or require a released version once available) and document it. | open |
| F14 | TLA | Docs, embedded | Using the mp-units support in an embedded, `-fno-exceptions`, `-Werror=undef` build needs undocumented setup: mp-units must be included as system headers (its headers test undefined macros such as `MP_UNITS_COMP_MSVC`), and `MP_UNITS_HOSTED=0` is required because the hosted `inplace_vector::emplace_back` throws. With that setup the `[m, m/s]` example costs 18 bytes on Cortex-M4. | Phase 3 probe (`mp_probe.cpp`) on GCC 14/15, clang 20/21, Arm GCC 15.2. | Document an embedded configuration for the mp-units support (system includes, `MP_UNITS_HOSTED=0`, `MP_UNITS_API_CONTRACTS=0`) and cover it in the CI job proposed in F4. | open |
| F15 | TLA | Packaging | The integrations with strong-type libraries (mp-units, Au, nholthaus, chrono backends) are "example plug-ins" under `support/`, which the install rules do not ship: only `include/` is installed. A consumer must copy the glue (for example the mp-units `element_caster` and tuple-decomposition specializations) or reach into the example directory, as ArduPilot now does through the submodule path `support/mp_units`. | `include/CMakeLists.txt` install rules; README "Plug-ins" table. | Ship the strong-type integrations as installed, optional headers (for example `fcarouge/typed_linear_algebra/mp_units.hpp`), keeping only backend examples in `support/`. | open |
| F16 | Kalman | Usability | Using Kalman with typed matrices requires specializing internal customization points, `kalman_internal::evaluates`, `transposes`, `one` and `zero`, for `typed_matrix`, and `one`/`zero` for mp-units quantities (a 1x1 typed product collapses to a quantity). These specializations exist only in example facades (`support/eigen_typed`, `support/quantity`, `support/mp_units/unit.hpp`). | `AP_LinearAlgebra_Kalman.h` had to copy them for the ArduPilot backend. 2026-10-09: the points moved to `fcarouge::kalman_filter::internal`, still internal | Ship the typed integration as a public, installed header with documented customization points outside `kalman_internal`. | open |
| F17 | Both | Packaging | The mp-units `element_caster` specializations are defined twice: in Kalman `support/quantity/fcarouge/linalg.hpp` and in TypedLinearAlgebra `support/mp_units/fcarouge/mp_units.hpp`; including both would redefine them. | Both files. | Keep one owner (TypedLinearAlgebra) and have Kalman use it. | open |
| F18 | Both | Usability | The backend contract includes divisions that only form types: Kalman takes `state / state` (transition matrix type) and `scalar / state` (output model type for a scalar output). TypedLinearAlgebra's `operator/` deduces its return type, which instantiates the backend division body even in type-only contexts, so a backend cannot declare these as unsupported: it must implement non-square right division (Eigen-like minimum norm / least squares semantics). Undocumented. | `x_z_p_q_r_hh_f_us_ps.hpp` deduction, `divide.tpp`; a `static_assert` in the backend's non-square branch fired. | Compute these types without evaluating a division (type traits), or document the full division contract. | open |
| F19 | TLA | Usability | Withdrawn, inaccurate. The element setter is `at<i...>(const element &)`, at the pinned and later versions: temporaries, `const` values, equivalent unit expressions such as `(m/s) * m^2 / m^3` for `1/s`, and other units of the same dimension (km for m) are accepted, a wrong dimension is rejected. The named variables in the thermal EKF were a workaround for F20 (single index access on a 1x4 matrix), misattributed here. | Re-tested 2026-10-09 with g++ 15 on TypedLinearAlgebra 8eb0b1c and c9a5c2b; the thermal EKF output model now sets elements from temporaries. | None. | withdrawn |
| F20 | TLA | Usability | A 1xN or Nx1 typed matrix is rank 1 and rejects two-index access (`element<0, j>`, `at<0, j>`) through a sentinel type with deleted special members; the error is "use of deleted function ~type()". Generic filter code (an output model is z x n) breaks when the output count is 1. Likewise a 1x1 typed vector is rank 0 and rejects `at<0>()`, requiring `at()`. | Thermal EKF output model, 1x4; again generic element type traits in `AP_LinearAlgebra` (`ElementType`), which must dispatch on the shape because `element<i, j>` is unusable on vectors.; also the cause of the thermal EKF's named element variables first attributed to F19 | Allow full-rank indexing on vectors (index 0 on the unit dimension), or a readable `static_assert`. | open |
| F21 | Kalman | Embedded | `one<>` and `zero<>` are non-`constexpr` `inline` variable templates: each instantiation is a global object with dynamic initialization. The 4-state thermal EKF uses 360 B of RAM (data + bss) for them on Cortex-M4, and 4072 B of code versus 1040 B for the hand-written filter it replaces. | `arm-none-eabi-size` of the probe and of `AP_Soaring/ExtendedKalmanFilter` + `matrixN`. | Make them `constexpr` (or functions) so they fold into code, and track code size per sample in CI. | open |
| F22 | Both | Build | Compile cost per translation unit (g++ 15, `-O2`): `kalman.hpp` 2.2 s / 154 MB, `typed_linear_algebra.hpp` 2.1 s / 185 MB (about 1.3 s of each is `<format>`/`<print>`, see F2), with TypedLinearAlgebra's mp-units support 5.8 s / 383 MB. Including them from a widely included header would add minutes to an ArduPilot build; ArduPilot confines them to one source file. | Header-only compile timing.; re-measured 2026-10-09 with `-fsyntax-only` (not comparable with the figures above): `kalman.hpp` 1.6 s / 150 MB, `typed_linear_algebra.hpp` 2.0 s / 180 MB, mp-units support 6.0 s / 370 MB | Split formatting out (F2), offer forward declarations for the filter type, and keep heavy machinery out of the main include path. | open |
| F23 | Kalman | Usability | Supported filter configurations are an enumerated list: a configuration without initial P, Q and R (set later, as ArduPilot does on each thermal entry) fails with "This requested filter configuration is not yet supported" without saying which configurations are accepted. | `kalman_internal/factory.hpp:69`. | Default P, Q and R to zero when omitted, and list the accepted configurations in the diagnostic. | open |
| F24 | Kalman | Usability | Spelling the matrix types a filter needs (covariance, output model, output variance) requires internal names: `kalman_internal::ᴀʙᵀ`, `evaluate`, `quotient`, `product`; `ᴀʙᵀ` is a non-ASCII identifier, which many code bases and style checkers reject. | Kalman unit samples; ArduPilot uses `AP_LinearAlgebra::OuterProduct` and `Quotient` wrappers instead. 2026-10-09: now `kalman_filter::internal`, `ᴀʙᵀ` unchanged | Public, ASCII aliases, for example `fcarouge::covariance<State>` and `fcarouge::output_model<Output, State>`. | open |
| F25 | TLA | Build | `typed_matrix::data()` returns `std::forward_like<decltype(self)>(self.storage)`. With clang (20, 21) and Ubuntu 24.04's default libstdc++ 14.2, whose `std::forward_like` has a deduced `decltype(auto)` return type, this fails: "function 'forward_like<...>' with deduced return type cannot be used before it is defined". libstdc++ 14.3 and 15 rewrote it with an explicit return type and work. | CI `test unit tests and sitl building (clang, ...)` on `test_linear_algebra`; libstdc++ `bits/move.h` 14.2 versus 14.3. | Avoid `std::forward_like` (an explicit cast on the deduced `self` category), or document libstdc++ >= 14.3 for clang. | open |
| F26 | TLA | Features | No typed block, segment or concatenation operations: a heterogeneous state vector such as EKF3's 24 states is used by groups (velocity, position, biases), and covariance updates work on blocks, but TypedLinearAlgebra only offers element access (`at<i>()`) and whole-matrix algorithms. Mapping EKF3's union of a state struct and a `Vector24` onto one typed vector would need per-element code. Nested typed matrices (`support/nested_typed_eigen`) may be the intended route; undocumented for this use. | TypedLinearAlgebra public API and README; EKF3 `state_elements`. | Typed `block<Row, Column, Rows, Columns>()` views or copies with their element types, and concatenation of typed vectors, or documented guidance for grouped states. | open |
| F27 | TLA | Usability | A unit mismatch is reported as "Matrix addition requires compatible element types" without the position or the two element types involved; in a 9x9 normal matrix the developer must guess which element is wrong. | Deliberate mistake in the accelerometer calibrator (a unitless residual) in `add.tpp:86`. | Report the first incompatible position and both element types, for example with a per-element `static_assert` in an index-expanded check. | open |
| F28 | TLA | Embedded | No compound assignment (`+=`, `-=`, `*=`) and no in-place algorithms: every typed operation returns a new matrix, and the wrappers copy whole backend matrices. `JTJ = JTJ + transposed(J) * J` on 9x9 floats needs a 1336 B stack frame on Cortex-M7 (ArduPilot limit 1300 B, `-Werror=frame-larger-than`), where the hand-written loop needs none beyond JTJ. ArduPilot works around it by type-checking the expression with an unevaluated `decltype` and accumulating on the backend storage. | `AP_AccelCal/AccelCalibrator.cpp` (CubeOrange, MatekF405 builds); again in `AP_Compass/CompassCalibrator.cpp`, where JTJ is also damped in place twice instead of copied, to fit the 2048 B calibration thread stack. | Compound assignment operators delegating to the backend's in-place operations, and move/forwarding through `make_typed_matrix` so temporaries are not copied. | open |
| F29 | TLA | Embedded, build | `typed_linear_algebra.hpp` always includes the `std::chrono` integration (`chrono.tpp`, `<chrono>`) and `<format>`. ArduPilot defines `floor`, `exp`, `pow` and other double precision maths functions as function-like macros on boards without a double precision FPU; `<chrono>` parsed after them fails ("macro 'floor' passed 2 arguments"). ArduPilot saves and restores the macros around the includes. | MatekF405 copter build with the typed accelerometer calibrator; `AP_HAL/AP_HAL_Macros.h`. | Make the chrono and format integrations opt-in headers; keep the core header to `<tuple>`, `<concepts>`, `<utility>`. | open |
| F30 | TLA | Portability | Does not compile with the libc++ of current LLVM (emscripten 6.0.8, clang 24), even for a 2-element mp-units vector: `typed_matrix` reads `std::tuple_size_v<row_indexes>` (`typed_linear_algebra.hpp:195`); TypedLinearAlgebra's `std::tuple_size` specialization for typed matrices is constrained by concepts (`rank_typed_matrix`, `same_as_typed_matrix`) whose `std::same_as` instantiates the `std::tuple`; libc++'s C++23 tuple-like `operator<=>` then needs `tuple_size_v` of that same tuple, whose initializer is still being evaluated: "non-type template argument is not a constant expression" (`tuple:344`). Completing the index tuples beforehand avoids it for user-visible types, but not for the tuples TypedLinearAlgebra computes internally (products, quotients, `make_typed_matrix` in `typed_linear_algebra.tpp:362`). Native clang 20/21 with their libc++ and libstdc++ 14/15 are not affected yet. Pinning an older emscripten is no way out: 4.0.20 fails earlier, in mp-units `master` (`absolute_zero` does not satisfy `PointOriginFor`), which TypedLinearAlgebra requires (F13). | ArduPilot `test WebAssembly Plane` CI and local emscripten 6.0.8 build of the typed accelerometer calibration; minimal reproducer with `ColumnVector<float, m/s^2, 1>`.; again with emscripten 6.0.8 (CI version) on the Kalman soaring EKF, `objs/AP_Soaring` | Constrain the `std::tuple_size` specialization without instantiating arbitrary tuples (for example on a cheap trait of the `typed_matrix` template), and add an emscripten or libc++-trunk CI job. | fixed (TypedLinearAlgebra c9a5c2b: WebAssembly Plane with emscripten 6.0.8 builds with the thermal EKF and the accelerometer, compass and polynomial fits) |
| F31 | TLA | Features | No typed diagonal operations: extracting the diagonal of a heterogeneous square matrix as a typed vector, building a typed diagonal matrix from a typed vector, or adding a typed vector to a diagonal. These are what dimensionally consistent least-squares damping (Marquardt's lambda * diag(J^T J)) and covariance regularization need; the "identity" of a heterogeneous normal matrix has diagonal elements of different units, so `one<>`-style identities do not apply. | ArduPilot `CompassCalibrator` Levenberg-Marquardt damping (see the plan, Phase 6): the port adds lambda to the backend diagonal in place, outside the type system. | `diagonal(m)` returning a typed vector of the diagonal element types, `diagonal_matrix(v)`, and `add_to_diagonal(m, v)`. | open |
| F32 | TLA | Correctness | Matrix division `a / b` derives its result type from the first column index of `a` and of `b` only, without checking that `x * b` has the type of `a` (`@todo Add type verification` in `divide.tpp`): a dimensionally inconsistent equation compiles and yields a wrongly typed result. There is also no way to choose the decomposition (symmetric positive definite normal matrices, the common case, suit Cholesky without pivoting, cheaper on stack and with a unit-consistent singularity test). | A test dividing a unitless row by a normal matrix in m^2, m*s, s^2 compiled with a unitless result; `AP_LinearAlgebra::divide_positive_definite()` now checks the product element by element. | Verify division with the product's type rules (a `static_assert` on `x * b` against `a`); offer a division or solve that names its decomposition. | open |
| F33 | TLA | Features | All elements of a typed matrix share the backend's scalar type: the mp-units plug-in requires each quantity's representation to equal the storage type. A state that mixes precisions, such as ArduPilot's `[position, velocity, acceleration]` with a `double` position (`postype_t`, for metre-level resolution far from the origin) and `float` velocity and acceleration, cannot be one typed vector without widening every element to `double`. | Probe: `ColumnVector<double, quantity<m, double>, quantity<m/s, float>>` and the `float` storage variant both fail the `element_caster` static assertion (TypedLinearAlgebra c9a5c2b). | Allow per-element representations (a tuple-like backend, or storage of the common type with exact per-element casts), or document the single-representation requirement. | open |
